# doc-to-json

CLI, который получает текст документа (счёт, КП, акт) и возвращает JSON по фиксированной схеме.
Цель — не дать модели уверенно выдумать то, чего в документе нет.

## Запуск

### Вариант 1: локально

Нужны Python (проверено на 3.14) и [Ollama](https://ollama.com) с моделью, поддерживающей structured outputs.

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

python -m extractor data/01_invoice.txt     # один документ -> JSON в stdout
python eval.py                              # весь набор -> отчёт
python -m pytest                            # пустой вход и плохие ответы модели, Ollama не нужен
```

`make` не используется: одна команда eval — `python eval.py`.

### Вариант 2: Docker

Нужен только Docker. Одна команда поднимает Ollama, при первом запуске скачивает модель
`qwen3.6:35b-a3b` (21,7 ГБ) и прогоняет eval:

```bash
docker compose up --build
```

Отчёт печатает сервис `app`. Ollama после этого продолжает работать — остановить: `Ctrl+C` или `docker compose down`.

```bash
docker compose run --rm app python -m extractor data/01_invoice.txt   # один документ
docker compose -f compose.yaml -f compose.gpu.yaml up --build          # то же с NVIDIA GPU
```

Без `compose.gpu.yaml` модель работает на CPU: запустится на любой машине, но медленно.
Другая модель из реестра Ollama задаётся в файле `.env`, например `OLLAMA_MODEL=qwen3:4b`.

Отчёт в разделе Eval получен в варианте 1 на локальной сборке модели. Публичная `qwen3.6:35b-a3b` —
другой файл весов, её результат может отличаться.

Модели хранятся в отдельном volume. Папку моделей Ollama с хоста в контейнер подключать не стоит:
Ollama в образе может быть новее и при старте меняет формат хранилища.

## LLM

Платного ключа нет, поэтому модель локальная, через Ollama. Вызов настоящий, не мок.
Отчёт ниже получен на `qwen3.6-35b-a3b-agent` (Qwen 3.6 35B, Q4_K_M). Другая модель:

```bash
set OLLAMA_MODEL=имя-модели       # Linux/macOS: export OLLAMA_MODEL=имя-модели
```

Температура 0, режим размышления выключен: с ним документ обрабатывается около 100 секунд, без него около 9,
а на тестовом наборе точность без размышления уже максимальная.

## Пайплайн

| Шаг | Файл | Что делает |
|---|---|---|
| 1. Вызов LLM | `extractor/llm.py` | Системный промпт с правилами + текст документа; структура ответа задана грамматикой |
| 2. Валидация ответа | `extractor/schema.py`, `Answer` | pydantic в строгом режиме: типы, enum, дата ISO, суммы ≥ 0, confidence 0..1, лишние ключи запрещены |
| 3. Сверка с текстом | `extractor/grounding.py` | Значения, которых нет в исходном тексте, обнуляются; БИН приводится к 12 цифрам |
| 4. Итоговая валидация | `extractor/schema.py`, `Document` | Тот же строгий режим плюс БИН ровно 12 цифр. Наружу выходит только `Document` |
| Оркестрация | `extractor/pipeline.py` | Повторы при невалидном ответе, запасной результат |

Схема проверяет форму ответа, но выдуманный БИН из 12 цифр формально валиден. Поэтому шаг 3 — отдельная
детерминированная проверка содержания, не зависящая от модели.

### Почему грамматике отдаётся только структура

Ollama ограничивает ответ JSON Schema на уровне генерации токенов. Первая версия передавала схему целиком,
вместе с `format: date` и `pattern`, и eval показал `doc_date` 4/10: модель хотела написать `12.11.2026`,
грамматика подгоняла это под шаблон, и получалась валидная, но неверная дата `1211-11-20`. Валидация её
пропускала. Жёсткая грамматика не ловит ошибку значения, а маскирует её.

Теперь из схемы для LLM убраны ограничения на значения (`format`, `pattern`, `minLength`, `minimum`,
`maximum`). Остаются ключи, типы и enum. Ошибку формата ловит pydantic, и она уходит в повтор с текстом ошибки.

## Проверка входа

- Файл не найден, не читается или не в UTF-8 — короткое сообщение в stderr и код выхода 1, модель не вызывается.
- Текст пустой или из одних пробелов — модель не вызывается; возвращается тот же пустой документ, что и после
  трёх невалидных ответов (см. ниже), с причиной в `warnings`.

## Что происходит, если ответ не прошёл валидацию

1. Текст ошибок pydantic возвращается модели с просьбой исправить JSON. Всего до 3 попыток.
2. Если все попытки невалидны, система отдаёт валидный по схеме пустой документ: `doc_type: "unknown"`,
   все поля `null`, `line_items: []`, все confidence `0.0`, в `warnings` — причина. Невалидный JSON наружу
   не выходит никогда; такой документ уходит на ручной разбор, а в eval считается пропусками.
3. Каждая неудачная попытка пишется в stderr.

Оба сценария воспроизводятся тестами `tests/test_pipeline.py` с подменённой LLM.

Нечитаемый БИН к этому сценарию не относится: он обнуляется на шаге 3 по полю, остальные данные документа
сохраняются. Иначе один испорченный реквизит стоил бы всего документа.

## Правила заполнения

| Ситуация | Правило |
|---|---|
| Значения нет в документе | `null`. Не выводим БИН из названия, не подставляем дату, не складываем позиции в итог |
| НДС | Только сумма, написанная числом. «Без НДС», «НДС не облагается», указана лишь ставка — `null` |
| Противоречие (две даты документа, две суммы «итого», сумма цифрами ≠ сумме прописью) | Берётся значение, которое встречается в тексте **первым**; в `warnings` — оба значения |
| Не противоречие | «Итого» без НДС и «Всего к оплате» с НДС (берётся сумма к оплате); дата документа и срок действия/оплаты |
| Ошибки OCR в цифрах | Исправляются только однозначные замены (`l`, `I` → 1; `O` → 0) + warning. В датах и суммах это делает модель, в БИН — код |
| БИН после OCR | Модель переписывает его как в документе. Если после замен получилось ровно 12 цифр — значение принимается, confidence ≤ 0.5, warning. Иначе `null` + warning |
| Название на двух языках через «/» | Первый вариант |
| `supplier_name` | Как в документе, вместе с формой собственности (ТОО, ЖШС, ИП) |
| `total_amount` | Сумма к оплате; сумма прописью переводится в число |

### Сверка с текстом (в коде)

| Поле | Проверка | Если не прошло |
|---|---|---|
| `supplier_bin` | После OCR-замен это 12 цифр, и они есть в тексте | `null`, confidence 0, warning |
| `doc_number` | Значение есть в тексте (без учёта пробелов и регистра), допускаются OCR-замены | `null`, confidence 0, warning |
| `vat_amount` | Цифры суммы есть в тексте | `null`, confidence 0, warning |

`total_amount` и `doc_date` не сверяются намеренно: они бывают записаны прописью («сто двадцать тысяч»,
«09 қазан»), и буквальная проверка обнуляла бы верные значения.

`field_confidence` — самооценка модели по каждому полю; код её только понижает (см. таблицы).

## Тестовый набор

`data/NN_*.txt` — документ, `data/NN_*.json` — эталон. Эталоны проверяются той же pydantic-схемой.

| № | Документ | Что проверяет |
|---|---|---|
| 01 | Счёт на оплату (из ТЗ) | Базовый случай; «Итого» и «Всего к оплате» — не противоречие |
| 02 | Коммерческое предложение (из ТЗ) | Нет БИН, номера, итога; срок действия — не дата документа |
| 03 | Шот-фактура (из ТЗ) | Каз/рус текст, OCR в БИН, сумма прописью, «НДС не облагается», номер `AKT-09` у счёта-фактуры |
| 04 | Акт выполненных работ | Два БИН (исполнитель и заказчик), НДС «в том числе» с копейками |
| 05 | Invoice в EUR | Иностранный поставщик: VAT ID — не БИН, reverse charge — не сумма НДС |
| 06 | Счёт с противоречиями — **сложный** | Две даты счёта и две суммы (цифрами и прописью) |
| 07 | Акт без реквизитов — **сложный** | Нет БИН, номера, даты, цены; сумма только прописью |
| 08 | Счёт после OCR — **сложный** | БИН не восстанавливается (11 цифр), OCR в дате и суммах |
| 09 | КП на казахском и русском — **сложный** | Казахские месяцы, БСН, «цены без НДС», срок действия |
| 10 | Письмо о смене реквизитов | `doc_type: unknown`, сумм нет, `KZT` внутри IBAN — не валюта |

## Eval

`python eval.py` прогоняет все документы через тот же `extract()`, что и CLI, и печатает:

- **точность по каждому полю** — значение совпало с эталоном после нормализации (регистр, кавычки, пробелы);
  `line_items` — одно поле, верно, только если совпал весь список;
- **галлюцинации** — поле заполнено, а в эталоне `null` (для `line_items` — пустой список);
- **пропуски** — `null`, а в эталоне есть значение.

Неверное значение при заполненном эталоне снижает точность, но не входит ни в один из двух счётчиков.
`warnings` сравниваются по наличию (есть / нет) и в ИТОГО не входят; `field_confidence` не сравнивается.

Результат на `qwen3.6-35b-a3b-agent`, 10 документов за 90 секунд:

```
Поле            Точность  Галлюцинации  Пропуски
doc_type           10/10             0         0
supplier_name      10/10             0         0
supplier_bin       10/10             0         0
doc_number         10/10             0         0
doc_date           10/10             0         0
currency           10/10             0         0
total_amount       10/10             0         0
vat_amount         10/10             0         0
line_items         10/10             0         0
ИТОГО              90/90             0         0
warnings*           9/10             1         0
* сравнивается только наличие предупреждений; в ИТОГО не входит

Расхождения:
  07_missing_fields_sum_in_words / warnings: ожидалось None, получено True
```

Единственное расхождение — лишнее предупреждение в документе 07: модель сообщила, что перевела сумму из
прописи в число, хотя промпт просит об этом не предупреждать.

## Ограничения

- **Цифры оптимистичны.** Промпт дорабатывался на этих же 10 документах, отложенной выборки нет. Это проверка
  работоспособности пайплайна, а не оценка качества на реальном потоке.
- **`warnings` проверяются по наличию.** Если в документе два противоречия, а модель заметила одно, eval этого
  не увидит. Так и было в документе 06 до уточнения промпта; найдено ручным просмотром.
- Сверка с текстом — фильтр, а не доказательство: БИН заказчика тоже есть в тексте, и его подстановку
  вместо БИН поставщика ловит только eval.
- `total_amount`, `doc_date` и позиции защищены только промптом.
- `field_confidence` не калибрована: модель почти везде ставит 1.0.
- **Размер документа не проверяется.** Текст длиннее контекста модели Ollama обрезает молча и с начала:
  при проверке (контекст 2048 токенов, документ на 17 тысяч символов) в модель попал только хвост документа,
  без системного промпта, и ошибки не было. Локальная сборка модели работает с контекстом 32768 токенов.
  В Docker на машине с 8 ГБ видеопамяти Ollama выбрала контекст 4096 токенов — по оценке, это около
  8 тысяч символов документа.
